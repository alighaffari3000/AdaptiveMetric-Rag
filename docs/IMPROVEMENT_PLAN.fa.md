# نقشه اجرایی بهبود معماری AdaptiveMetric RAG

تاریخ تهیه: ۱۴۰۵/۰۶/۱۴ (2026-09-05)
مبنا: بررسی کد نسخه فعلی (`app/retrieval.py`، `app/embeddings.py`، `app/documents.py`، `app/providers.py`، `app/main.py`)

## خلاصه

ایده اصلی پروژه (تغییر ترکیب معیارهای شباهت بر اساس نیت سؤال) حفظ می‌شود. سه پایه ضعیف فعلی جایگزین می‌شوند:
امبدینگ هش‌شده که معنایی نیست، اسکن کامل بدون ایندکس، و مسیریاب نیت انحصاری مبتنی بر لیست کلمات.
کارها در ۸ فاز چیده شده‌اند. فاز ۰ (مجموعه ارزیابی) پیش‌نیاز همه فازهاست، چون بدون آن هیچ تغییری قابل اندازه‌گیری نیست.

وضعیت اندازه‌گیری‌شده فعلی:

| سنجه | مقدار فعلی |
|---|---:|
| زمان بازیابی با ۱٬۰۰۰ چانک | ۲۴۰ میلی‌ثانیه |
| زمان بازیابی با ۵٬۰۰۰ چانک | ۱٬۰۷۶ میلی‌ثانیه |
| زمان بازیابی با ۲۰٬۰۰۰ چانک | ۵٬۱۱۲ میلی‌ثانیه |
| شباهت سؤال فارسی با معادل انگلیسی (امبدینگ پیش‌فرض) | ۰٫۰۰ |
| شباهت «هزینه قرارداد چقدر است؟» با جمله واقعی مبلغ | ۰٫۱۵ |
| شباهت همان سؤال با «قرارداد قرارداد قرارداد قرارداد» | ۰٫۴۲ |

## ترتیب و وابستگی فازها

```
فاز ۰ (ارزیابی)
  └─► فاز ۱ (ایندکس و کارایی)
        └─► فاز ۲ (امبدینگ معنایی)
              └─► فاز ۳ (ترکیب و بازترتیب)
                    ├─► فاز ۴ (درک سؤال و حافظه مکالمه)
                    ├─► فاز ۵ (ورودی و قطعه‌بندی)      ← موازی با ۴
                    └─► فاز ۶ (تولید پاسخ و ارجاع)      ← موازی با ۴ و ۵
فاز ۷ (عملیات و امنیت) ← مستقل؛ هر زمان
```

برآورد کل برای یک توسعه‌دهنده: ۳ تا ۵ هفته.

## فاز ۴ — درک سؤال و حافظه مکالمه (۳ تا ۴ روز)

هدف: مسیریاب چندبرچسبی، بازنویسی سؤال با تاریخچه، نرمال‌سازی درست فارسی.

### کارها

- [ ] ماژول `app/text.py`: نرمال‌سازی یکپارچه فارسی (ی/ک عربی، نیم‌فاصله، کشیده، اعراب، اعداد فارسی/عربی → لاتین). همه جا (ingest، query، FTS) از همین تابع استفاده شود.
      نکته: الگوی سال `1[34]\d{2}` در `DATE_RE` با «۱۴۰۲» فارسی تطابق ندارد چون رقم‌های ۱ و ۴ لیترال هستند.
- [ ] تشخیص تاریخ جلالی (`۱۴۰۲/۰۳/۱۵`، «۱۵ خرداد ۱۴۰۲») و نگاشت به یک شکل استاندارد در سیگنال temporal.
- [ ] مسیریاب چندبرچسبی: هر نیت به‌طور مستقل امتیاز بگیرد؛ بردار وزن نهایی = میانگین وزنی بردارهای نیت‌های فعال. زنجیره `if/elif` حذف شود.
      تست: «چرا مبلغ قرارداد ۱۳۷ در سال ۱۴۰۳ تغییر کرد؟» باید هم‌زمان causal + numeric + temporal باشد.
- [ ] بازنویسی سؤال با LLM (یک فراخوانی ارزان با خروجی JSON) وقتی تأمین‌کننده غیرمحلی است:
  - سؤال مستقل (standalone) با توجه به ۳ تا ۴ نوبت آخر مکالمه
  - ۲ تا ۳ پرسش جایگزین (multi-query) که نتایجشان با RRF ادغام می‌شود
  - احتمال هر نیت، موجودیت‌ها و تاریخ‌ها
  - کش نتیجه بر اساس `(conversation_id, message)`
  - در حالت `local` همان مسیریاب قاعده‌محور چندبرچسبی به کار می‌رود
- [ ] بازیابی تاریخچه مکالمه در `chat()` و ارسال آن به بازنویس و به پرامپت تولید.
- [ ] حذف یا تنظیم‌پذیر کردن قانون `multi_part and len(clean) < 350` در `_looks_incomplete` که پاسخ‌های کوتاه درست را وارد حلقه ترمیم می‌کند.

### معیار پذیرش

## ریسک‌ها و تصمیم‌های باز

| ریسک | اثر | راهکار |
|---|---|---|
| حجم ایمیج داکر با torch و مدل‌ها | ایمیج از ~۲۰۰ مگابایت به ۱ تا ۳ گیگابایت می‌رسد | نسخه CPU torch، کش مدل روی volume، ایمیج جداگانه `-lite` با هش ویژگی |
| تأخیر بازترتیب‌دهنده روی CPU | ۱ تا ۲ ثانیه برای ۵۰ جفت | `rerank_top_n` قابل تنظیم، early-exit واقعی، گزینه LLM-rerank |
| هزینه فراخوانی LLM برای بازنویسی سؤال | یک فراخوانی اضافه به‌ازای هر پیام | کش، مدل ارزان، غیرفعال در حالت local |
| مهاجرت داده‌های موجود (BLOB، FTS، parent_id) | پایگاه‌های قدیمی | مهاجرت خودکار نسخه‌دار در `init_db` + reindex |
| انتخاب مدل امبدینگ پیش‌فرض | کیفیت در برابر حجم | تصمیم بعد از مقایسه e5-small و bge-m3 روی golden در فاز ۲ |

## معماری هدف (پس از فاز ۶)

```
پیام کاربر + تاریخچه
   │
   ▼
بازنویسی و تحلیل سؤال (قاعده‌محور یا LLM) → سؤال مستقل، multi-query، وزن‌های نرم نیت
   │
   ▼
مرحله اول: بردار معنایی (numpy/ANN)  +  FTS5 BM25  → ادغام RRF → ۳۰ تا ۵۰ کاندیدا
   │
   ▼
مرحله دوم: بازترتیب‌دهنده متقاطع + ویژگی‌های تطبیقی (entity/numeric/temporal/metadata)
   │
   ▼
اطمینان کالیبره → امتناع یا انتخاب چانک‌های والد
   │
   ▼
تولید استریم با ارجاع ساخت‌یافته → راستی‌آزمایی ادعاها → پاسخ + ارجاع‌های تأییدشده
```
