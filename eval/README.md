# Evaluation harness

Measures retrieval quality and latency so every change to the architecture can be
compared against a fixed yardstick. Recorded numbers live in `BASELINE.md`.

## Commands

```bash
python -m eval.run_eval                       # score the golden set, print a summary
python -m eval.run_eval --verbose             # also list failing cases
python -m eval.run_eval --tag cross_lingual   # score one slice
python -m eval.run_eval --json eval/results/run.json --markdown eval/results/run.md
python -m eval.run_eval --rewrite off         # score questions exactly as written
python -m eval.run_eval --rewrite llm         # measure the model-driven rewriter
python -m eval.bench_latency                  # latency at 1k / 5k / 20k chunks
python -m eval.make_fixtures                  # regenerate the two-page PDF fixture
pytest -m eval                                # the same golden run as a test
```

Every command builds a throwaway SQLite database in a temp directory and deletes
it afterwards, so the user's own `data/` is never touched. Set `EVAL_DATA_DIR` to
pin the location and `EVAL_KEEP_DATA=1` to keep it for inspection.

## Corpus

`corpus/` holds thirteen documents in Persian and English: two Persian contracts,
two English service agreements, an HR policy, a product manual, a GPU runbook, an
incident postmortem, a security policy, release notes in HTML, an invoice CSV,
creativity notes in Markdown, and a generated two-page PDF. Documents overlap in
topic on purpose, so a retriever cannot win by document-level topic matching
alone.

`annual-review.en.pdf` is generated by `make_fixtures.py` rather than committed as
a binary. Its cold-chain explanation deliberately straddles the page break.

## Golden set

`golden.jsonl` — one JSON object per line, `//` comments allowed.

| Field | Meaning |
|---|---|
| `id` | unique, stable case identifier |
| `question` | the query as a user would type it |
| `language` | `fa` or `en` |
| `intents` | intents a router should recognise (not scored yet) |
| `doc` | filename of the document that holds the answer |
| `must_contain` | every string must appear in a chunk for it to count as relevant |
| `any_contain` | at least one string must appear |
| `history` | prior conversation turns; the rewriter resolves the question against them |
| `expect_abstain` | true when the corpus cannot answer the question |
| `blocked_by` | phase that will make this case satisfiable; scored as a failure until then |
| `tags` | slices reported separately |

Cases carrying `history` are run through the offline rewriter by default, which
is what a `local` deployment does. `--rewrite off` scores the question as typed -
useful for separating a retrieval change from a rewriting one - and `--rewrite
llm` measures the model-driven rewriter, which costs one completion per case.

**Relevance is judged by content, never by chunk id.** Chunk ids change whenever
chunking, embeddings, or ingestion change; the golden file has to survive that.

## Metrics

| Metric | Meaning |
|---|---|
| `hit@5` | fraction of answerable questions with at least one relevant chunk in the top 5 |
| `recall@5` | fraction of all relevant chunks that appear in the top 5 |
| `mrr` | mean reciprocal rank of the first relevant chunk |
| `ndcg@10` | normalised discounted cumulative gain over the top 10 |
| `answerable_not_abstained` | fraction of answerable questions the gate did not refuse |
| `abstain_accuracy` | fraction of unanswerable questions the gate correctly refused |

## Adding a case

1. Add the answer text to a corpus document, or point at one that already has it.
2. Append a line to `golden.jsonl` with a distinctive `must_contain`.
3. Run `python -m eval.run_eval`; the validator fails loudly if no chunk can ever
   satisfy the case, which almost always means a typo in `must_contain`.
